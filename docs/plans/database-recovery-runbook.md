# 隔離DB復旧の検収手順

状態: 開発用PGliteの合成データ復旧テストを実装。本番のバックアップ、復旧、提供再開は未検収。

要件の正本は [製品仕様 第24.5節](../specs/PRODUCT_SPEC.md)、操作承認は [本部の境界](EXECUTION_SCOPE.md)。この文書はDB復旧の手順と証拠の保存先であり、新しいサービスや復旧権限を作らない。

## 復元対象を混同しない

- 本人向けJSON書出しは閲覧用。未開示答案や内部の再送情報を除外するため、DBの完全バックアップではない。これを正式証拠の取込やアカウント再開に使わない。
- 開発用DBは既存PGliteの `dumpDataDir()` と `loadDataDir` で空の隔離DBへ戻す。[公式API](https://pglite.dev/docs/api)を利用し、独自のJSON復元処理は作らない。
- 本番PostgreSQL/Supabaseのバックアップ方法・暗号化・保管期間・実復元は、配備先と運用者の承認後に検収する。PGliteの成功で代替しない。

## 隔離ドリルの合格条件

合成データだけを使用し、元DBに上書きしない。保存確認済みの版・答案、正式証拠の改訂履歴、本人分離と失効拒否を復元先の既存サービスから照合する。テスト失敗時は提供再開の証拠に使わない。ログには答案本文や認証情報を出さず、成否とテスト名だけを記録する。

`web` ディレクトリで `npx tsx --test tests/database-recovery.test.ts` を実行する。テストはメモリー内の相談・習熟証拠・利用停止・再送記録をDBイメージから復元し、そのドリルで作った全表の行を比較する。製品全24表を実データで検収するテストではない。所有者の検査は既存サービス層の契約であり、本番DBロール/RLS復旧の証明ではない。取得後の更新・失効が失われる例も再現し、後述の照合を省略できないことを確認する。

## 本番復旧で残る必須条件

1. 利用受付と全書込みを止め、対象DB・バックアップ時刻・schema/application版・保管期限・実行責任者を確認する。実環境の操作は別承認とする。
2. 空の隔離先へ復元する。現行DBを破壊しない。実利用者から到達できない状態を維持する。
3. バックアップ取得後の削除・招待失効・教材撤回を独立した最新記録と照合し、復元先へ反映する。照合元が欠ける、時刻が不明、処理が未完了なら公開・再接続しない。バックアップ時点の失効記録だけでは、その後の削除要求を守れない。
4. schema、RLS/ロール、別利用者の読書き拒否、本人の保存確認済み答案、訂正履歴、再送抑止、失効利用者の拒否を検査する。認証、DB、教材を個別に成功扱いせず整合を照合する。
5. 復旧点と停止から検収までの実時刻を残し、仕様の暫定RPO/RTOと比較する。小さなfixtureの実行時間を本番の復旧時間へ換算しない。
6. 運用者の提供再開判断後に接続を切り替える。失敗時は隔離を保ち、元環境への復帰可否を判断する。バックアップの最長保持期間と削除依頼の反映確認も記録する。

最新の削除・失効記録を復旧DBと独立して維持する運用基盤は未検収。この条件が成立するまで、本番復旧・招待提供を完了とはしない。
