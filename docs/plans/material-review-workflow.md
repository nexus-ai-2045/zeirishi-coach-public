# 教材を提供するまでの手順

製品要件は [統合設計 第11・24.4節](../specs/PRODUCT_SPEC.md) を正本とする。この文書は実装への投入手順で、専門審査・著作権判断・公開承認を代行しない。

## 原稿と審査を分ける

教材の状態は `draft → expert_review → approved → active → retired`。開発用fixtureはこの状態機械に入れず、既存のローカル教材として隔離する。AIのレビューだけで専門審査を完了させない。

教材本文、4択と全選択肢の解説、期間図、原則の例外、AIが参照する根拠、試験形式への接続を一つの版として扱う。出典の利用条件・適用年度・科目と概念の対応も審査対象に含める。原稿の不備は承認欄を埋めて回避せず、原稿へ戻して修正する。

出典ごとに取得・保存・転載・改変・再配布・AI入力の可否を独立して確認する。規約URL、確認日、出典表記、個別許諾や例外の説明を保存する。「ネットで読めた」「有名な教材だった」は許諾の根拠にしない。許可が不明な用途は不許可として扱う。配信可能でもAI入力が許可されていなければAIへ渡さない。

## 人間が確認すること

1. 著者と別の専門レビュー担当が、対象科目・年度、原則と例外、正答・誤答理由、問題の解釈可能性を確認する。
2. レビューした内容全体のハッシュと確認日時・担当者識別子を記録する。担当者の個人情報を公開リポジトリへ載せない。
3. 出荷担当が利用条件と専門レビュー結果を確認し、同じ内容の版に対して有効化を承認する。アプリの公開・利用者招待は別の人間確認である。
4. 修正は新しい版として再審査する。既存答案を新しい教材で再採点せず、訂正の影響評価を行う。

ファイルに担当者名・ハッシュが書かれていることは、本人が承認した証拠の代わりにはならない。実際のレビュー記録と権限確認は運用者が照合する。実装の検査は、記録の欠落・内容の不一致・未承認版の混入を拒否するためのもの。

## 実装上の保存先

- 配信対象の登録元は `web/src/server/approved-catalog.ts` 一か所とする。概念一覧、計画候補、相談教材を別々に手入力して一致を祈る構成にはしない。
- 登録形式・内容照合の検査は `web/src/server/material-registry.ts`。この文書に型定義の写しを置かない。
- 教材版は退役・原稿を含む登録全体で一意にする。保存済み案件は教材版で参照するため、別教材に旧版IDを再利用しない。過去の登録を削除して版IDを再利用することも禁止する。
- 未審査教材は学習APIから取得できる場所へ置かない。候補のレビュー用共有も、利用条件と送信対象の人間承認を先に確認する。
- 現在の教材登録数は0件。チェックが通ったテストデータを、本物の承認記録や配信教材として登録しない。

## 今回と今後の境界

今回の登録経路は固定4択の実務練習用。教材の専門確認と、未見評価・合格ライン評価への適格性は別であり、登録だけで正式な評価証拠へ昇格させない。

複数active教材の選択と、本人の保存済み版による再開を実装している。同じ科目の概念は一つのパックとして供給し、異なる概念を選んだ開始要求を同一の再送として扱わない。退役・未登録の版は再開を拒否し、保存済み答案を別の版で再採点しない。

同じ概念を別の相談で練習できるよう、概念版と教材版を分ける。同時提供する同じ科目・概念のメタデータと概念版は一致させ、教材ID・教材版は案件ごとに区別する。概念一覧は一行に集約し、相談選択肢と週計画は教材IDを保持する。複数候補がある場合は明示選択を要求し、選択したケース版が変わっていれば開始を拒否する。再開は本人の保存済みケース版を使う。ケースを増やすだけで独立した問題ファミリーや正式評価用の問題数を満たしたとは扱わない。

教材編集・審査・有効化の管理画面、担当者の認証と操作監査、外部署名、退役版の再提供、訂正時の既存学習証拠の再評価は、まだ提供済みではない。登録検査をそれらの運用保証と呼ばない。
