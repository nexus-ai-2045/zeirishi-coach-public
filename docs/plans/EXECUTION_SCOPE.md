# 税理士コーチ本部：境界・ゴール・責務

更新日: 2026-10-13。

このファイルは「税理士合格への最短ルート」タスクの作業範囲・完了判定・分担の正本。チャットの途中報告や担当の局所的な成功で、この範囲を縮小しない。これは公開・課金・専門審査などの実行承認書ではない。

## 1. 全体ゴール

友人1人が招待ログインし、自分の理解度と受験予定に合わせて、実務相談・基礎概念・試験問題・AIへの説明・復習を一続きで学べるMVPを完成させる。保存、本人分離、費用制限、失敗時の復帰と運用手順まで実測し、人間が提供可否をレビューできる状態にする。

満点・利用時間・経験値ではなく、合格ラインに必要な実力の証拠を重視する。合格保証や根拠のない合格確率は提供しない。知らないことだけを学べること、既知の単元を飛ばせること、必要な単元へ直接進めることを維持する。

MVPの対象範囲・数量・品質基準は [PRODUCT_SPEC 第16・17・22節](../specs/PRODUCT_SPEC.md) を正とする。1科目パック、基礎概念6個以上、実務案件5本以上、人間レビュー済み練習60問以上と別の診断/評価プールなどを、合成相談1件で代替しない。全11科目分の教材を同時完成させる依頼ではない。

## 3. この本部で行うこと／行わないこと

本部で行うのは、製品仕様に沿った実装、既存部品の再利用、必要な調査、担当の分担、レビューの採否、統合、機能・画面・保存・運用の検証、残務の更新、人間判断の準備である。設計を毎回聞き直さず、通常の実装選択は既存仕様から判断して進める。

別件として切り分けるのは、汎用オーケストレーター、ai-round-table、cmux、他プロジェクトのリファクタ、アプリ全体のモデル設定などの改善である。製品を進めるために必要な利用・限定診断は行えるが、それらの基盤改修を本部の主目的に置き換えない。連携が止まっても独立した製品実装を続ける。

製品仕様で除外されている実際の申告・税務代理、実在顧客データ、一般公開・課金機能、オフライン学習、旧CLIログ移行などを無断で追加しない。

## 4. 責務の分担

| 主体 | 責務 | 勝手に行わないこと |
| --- | --- | --- |
| Codex本部（このタスク） | 全体ゴールの保持、優先順位、担当境界、設計との照合、レビュー採否、統合、結果回収、全体完了判定、人間判断の提示 | 局所テストを製品完成とすること、未承認の外部操作、専門審査の代行 |
| 実装担当エージェント | 指定されたファイル/機能の実装、変更に見合う検査、差分と未完了事項の返却 | 他担当の変更の巻戻し、担当外の設計確定・公開・権限拡張 |
| テスト担当エージェント | 受入条件に沿った独立テスト、失敗の再現、画面や保存状態の証拠の返却 | mockや合成教材の成功を実環境検収とすること |
| レビュー担当（Claude Code等を含む） | バグ・境界漏れ・要件不一致の指摘と根拠、修正確認 | 指摘だけで本部の採否・人間承認を置き換えること |
| ユーザー／運用者 | 対象サービス・費用・配備・招待・公開/外部送信の判断、必要な資格情報の安全な設定、提供可否の最終レビュー | 秘密情報のチャットや公開ファイルへの貼付けは不要 |
| 教材・模試の専門レビュー担当 | 内容・年度・根拠・比較可能性の実際の審査と記録 | AIによる形式チェックを専門承認の代用とすること |

担当名は固定的な権限ではない。委任ごとに所有ファイル・返却物・停止条件を明示し、本部が結果を回収する。担当が終了・失敗したら進行中と報告しない。特定のAIや連絡手段が使えない場合も、実行可能な本務を本部が引き取る。

## 5. 自律実行と人間判断の境界

既存仕様に沿うローカル実装・テスト・文書更新・限定レビューは進める。既存変更を壊さず、同じロジックの写しを増やさず、失敗は原因のある共通箇所へ戻して修正する。

次は対象と操作を具体化した人間判断が必要である。

- APIの資格情報・利用開始と費用、外部サービスの選択/作成/復旧。
- 実DBへのmigration・権限適用・破壊的操作、実環境への配備。
- 教材/総合模試の取得・利用条件・専門承認・有効化、実利用者の招待。
- PR/push等の外部送信、公開範囲変更、公開・投稿・リリース。
- native GUI操作など、現在の安全指示で個別承認が必要な操作。

判断待ちは依存部分に限定する。例えばAI接続待ちを、非AIの保存・学習導線・診断/復習実装まで止める理由にしない。新しい権限や費用を「ブロッカーなので事後承諾」で取得しない。

## 6. 完了を判定する単位

1. **実装済み**: 仕様に対応するコードと必要なテストが存在し、担当結果を統合した状態。
2. **ローカル検証済み**: 対象フロー、異常系、本人分離、画面操作などを記録付きで確認した状態。mockや隔離DBの範囲を明示する。
3. **提供準備完了**: 製品仕様のMVP受入条件、承認教材、AI品質/費用、実Auth/DB、保存/失効競合、復旧、主要端末の通し操作を検収し、人間レビューへ渡せる状態。
4. **提供・運用検収**: 明示承認後の配備/招待/必要なPR等について外部の実結果を回収した状態。未承認の操作を自動で行ってこの段階へ進めない。
5. **学習効果の確認**: 仕様の4週間パイロットを実施して別途判定する。MVP実装完了を学習効果実証と呼ばず、1名の改善を一般的な合格率改善と呼ばない。

本部の全体ゴールを1・2だけで完了扱いにしない。4週間の結果がまだなければ追跡事項として残す。各段階で、残る要件・担当・次の操作・必要な人間判断を照合する。保証という言葉ではなく、検証した範囲と残る制約を示す。
